# Streamed file digests

`FileDigests.read(Path)` computes SHA-256, GNU debuglink CRC32 and a `long`
byte count in one pass with a 64 KiB buffer. It reads the supplied path using
normal filesystem semantics and returns lowercase SHA-256 plus an unsigned
32-bit CRC in a Java `long`. The overload accepting a cancellation callback
checks before opening, between reads and after EOF. It closes its stream on
success, failure and cancellation; a failed close cannot return a successful
result. Zero-progress reads fail instead of spinning. Cancellation cannot
interrupt an already blocked filesystem read.

The values describe the bytes observed during that read. They do not establish
a stable snapshot, file identity, ELF compatibility or permission to attach a
sidecar. Concurrent edits can affect the observed bytes. In particular, a null
Java `fileKey` is not an identity: the pinned Windows JDK returns null for that
attribute. Identity, metadata, receipts and the attachment transaction remain
separate work under [ADR-0004](ADR-0004-DEBUGLINK-ATTACHMENT.md).

The existing export-report and packaged-native SHA callers share this helper.
They retain their previous cancellation behavior, including finishing report
hashes after pair publication. The report schema and imported-input SHA guard
are unchanged. No attachment option, ELF section writer or native call is added.

The [GDB separate-debug-file contract](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Separate-Debug-Files.html)
defines the reflected IEEE CRC32 over the complete sidecar, initialized and
finalized with inversion. The helper uses Java's `CRC32`, not CRC32C. The value
is independent of target byte order; a future attachment encoder must serialize
it using the executable's byte order. Current integration tests compare the
value with Python `zlib` and the exact payload generated by target GNU `objcopy`
on private fixture outputs.

## Acceptance

The focused smoke checks known SHA/CRC vectors, binary contents, buffer edges,
short reads, failure/close exception ordering, zero progress, cancellation and
resource closure. It runs on Linux and native Windows. The integration harness
loads the helper from the installed extension JAR and verifies its class origin;
no locally recompiled production class can satisfy that check. Three actual
Forge fixture pairs per target cover executable, PIE and absent build ID. Their
SHA/CRC/counts must match an independent streaming Python oracle twice; GNU
debuglink basename, padding and target-endian CRC bytes must match exactly.
The original executable, source and sidecar contents/mtimes remain unchanged.

Linux x86 additionally uses an owned sparse input of 2,147,614,787 bytes, with
nonzero markers around buffer and signed-32-bit boundaries and at EOF. Both
Java runs use `-Xmx64m`; Python `hashlib`/`zlib` and GNU `sha256sum` independently
check the full input. The large input is removed after success or failure, while
the layout, hashes and logs are retained. This bounds digest memory, not Ghidra
analysis or export-model memory. Large-file results are attributed only to the
host where they run.

**CONFIRMED locally; hosted gate pending:** six focused checks pass on actual
Java 21, including packaged-native checksum rejection and report/path/publisher
regressions. Installed-JAR oracle runs pass on x86-64, AArch64 and MIPS32
big-endian, including the x86 large input. Nine fresh real exports pass GNU,
LLVM, strict libdwarf and GDB behavior; packaged export/path preservation and
deterministic reruns also pass. See `docs/VALIDATION.md` for exact evidence and
inherited diagnostics. The five-profile hosted matrix and native Windows are
still required. P2.8 remains incomplete and published releases are unchanged.
